## 1. ⚠️ `START_STICKY` не приводит к рестарту сервиса

**Воспроизводится стабильно, оба сценария.** Процесс убит через
`adb shell run-as com.horus.vpn.test kill -9 <pid>` при поднятом туннеле:

| Сценарий | Результат |
|---|---|
| Приложение на переднем плане | процесса нет 60 с, туннель не вернулся |
| Приложение в фоне (реалистичный OOM) | процесса нет 80 с, туннель не вернулся |

ActivityManager фиксирует смерть, но **не планирует рестарт**:
```
W ActivityManager: Exception when unbinding service com.horus.vpn.test/com.horus.vpn.HorusVpnTunnelService
I ActivityManager: Process com.horus.vpn.test (pid 13925) has died: fg +50 FGS
```
Строки `Scheduling restart of crashed service` в логе **нет вообще**.

При этом со стороны приложения всё выставлено правильно —
`dumpsys activity services` после смерти процесса:
```
app=null
startRequested=true      ← сервис всё ещё «нужен»
stopIfKilled=false
callStart=true
startCommandResult=1     ← START_STICKY
```
И приложение **в белом списке батареи**: `deviceidle whitelist` содержит
`user,com.horus.vpn.test,10722`.

**Что это значит.** Возврат `START_STICKY` корректен, состояние сервиса корректно,
исключение из оптимизации получено — и рестарта всё равно нет. Остаются две гипотезы,
и различить их на одном устройстве нельзя:

- **(а)** Transsion XOS подавляет перезапуск сервисов (в логе всюду `TABE`,
  `PowerHalWrapper`, `TranExceptionReporter` — собственный слой управления приложениями);
- **(б)** AOSP не перезапускает сервис, когда процесс убит внешним `SIGKILL`,
  а не самим ActivityManager.

⚠️ **Нужно решение, а не правка.** Прежде чем что-то менять, стоит проверить тот же
сценарий на «чистом» Android (Pixel / эмулятор). Если рестарт там происходит — это
OEM-специфика, и `START_STICKY` остаётся правильным решением с оговоркой в документации.
Если не происходит и там — sticky не является механизмом выживания, и опираться надо на
**Always-on VPN** (уже включается через `SUPPORTS_ALWAYS_ON`, см. §«подтверждено»)
плюс `BootReceiver`.

**Смягчающее обстоятельство** (обнаружено случайно, см. §2): фактически туннель
восстанавливается — но по другому пути, через сетевое событие при следующем запуске
приложения. То есть дыра меньше, чем кажется, но она не там, где задумывалось.

## 2. Автореконнект после рестарта процесса опережает восстановление сессии

**Наблюдение (дважды, независимо):**
```
17:27:50 W [recover] reconnecting in 0s (network Wifi)
17:27:50 I [intent] vpn intent set
17:27:52 E [recover] attempt failed: Нет активной сессии. Войдите в аккаунт.
17:27:52 W [recover] reconnecting in 10s (network Wifi)
17:27:55 W [recover] reconnecting in 0s (network Wifi)
17:27:58 I [tun] established, mtu 8500, socks 1080
```

**Механика.** `VpnManager` в конструкторе делает `_userWantsConnection = VpnIntent.Active`
и тут же `_network.Start()`. Стартовые `onAvailable` от `ConnectivityManager` дают
`OnNetworkChanged` → `RecoveryTrigger.Request` → через 3 с `OnRecoveryDue` видит
`State == Disconnected` и вызывает `ScheduleReconnect(immediate: true)`.

К этому моменту `ShellViewModel.EnsureStartedAsync()` ещё не восстановил сессию из
`StorageService`, и `ConnectAsync` падает на `GetServerConnectionAsync`.

**Последствия, по возрастанию:**
1. Одна попытка сгорает впустую;
2. `_reconnectAttempt++` выполняется **до** `ConnectAsync`, поэтому неудача по причине,
   не связанной с сетью, продвигает backoff (3 с → 10 с → 30 с → 2 мин);
3. На пути `BootReceiver` (и на sticky-пути, если он заработает) сессии на старте гарантированно
   ещё нет — то есть **первая попытка будет падать всегда**, а холодный старт после
   перезагрузки как раз тот случай, где задержка заметна.

**Направление правки:** реконнект должен ждать готовности сессии — либо гейт
`ConnectAsync` на «сессия загружена», либо не считать попытку израсходованной, когда
ошибка не сетевая (`SubscriptionExpiredException` / «нет сессии» → не инкрементировать
`_reconnectAttempt`).

## 3. Каждая строка журнала пишется дважды

**45 % событий в `events.jsonl` — соседние дубликаты** (108 из 238, интервал < 50 мс,
идентичный текст). Проверено на выгруженном архиве.

```
{"t":…,"c":"xray","m":"Config accepted (Hysteria2).", …}
{"t":…,"c":"xray","m":"Config accepted (Hysteria2).", …}
```

**Причина** — в `VpnManager.OnProtocolOutput`:
```csharp
Diag.Write(line);                  // (1)
_protocolLogBuffer.AppendLine(line);
_errorReporting.AppendLog(line);   // (2) → а он теперь тоже вызывает Diag.Write
```
`AppendLog` был переписан на форвард в `Diag` (чтобы журнал был один), но вызов
`Diag.Write` строкой выше не убран.

Дублируются только строки протокольного вывода — `[intent]`, `[tun]`, `[boot]` идут
через `Diag` напрямую и одиночны, что и подтверждает диагноз.

**Цена:** вдвое быстрее ротация 512 КБ, вдвое меньше полезной истории в кольце на 400
записей, вдвое больше записей на диск.

**Правка:** убрать `_errorReporting.AppendLog(line)` из `OnProtocolOutput` (одна строка).

## 4. `native.txt` хеширует все .NET-ассембли и топит снимок состояния

`state.txt` из архива — **494 строки, из них 449 в секции `native`**:
```
lib__Microsoft.Android.Resource.Designer.dll.so: 742cf285575f62be… 719 KB
lib_CommunityToolkit.Mvvm.dll.so: 982d799633cf692a… 160 KB
lib_GoogleGson.pdb.so: 9e0c16f0361fff2f… 178 KB
…ещё 440 строк…
```

`NativeInventory.Build()` берёт `Directory.GetFiles(nativeLibraryDir, "*.so")`, а .NET
Android упаковывает **каждую managed-сборку** как `lib_*.dll.so`. Отсюда:

- `state.txt` 32 КБ, `state.json` 37 КБ, `native.txt` 30 КБ вместо единиц КБ;
- SHA-256 считается по ~445 файлам, включая `libxray.so` на 55 МБ, — заметная работа
  на старте;
- **снимок состояния перестаёт выполнять свою задачу**: 45 полезных строк («скриншот
  вместо десяти сообщений в поддержку») погребены под 449 строками хешей.

**Правка:** брать только реально свои библиотеки — фильтр по именам
(`libxray.so`, `libhev_socks.so`) вместо `*.so`. Заодно исчезает и стартовая нагрузка.

> В Release-сборке с AOT состав будет иным, но шум останется: `lib_*.dll.so` — это
> механизм упаковки .NET Android, а не особенность Debug.

## 5. `[net]` публикуется 5.1 раза в минуту на неизменной сети

Замер по архиву: **134 публикации за 26 минут**, медианный интервал между всплесками
18 с, минимальный 4 с. Сеть при этом не менялась (Wi-Fi + LTE оба подняты, стабильны).

Каждая публикация — это `Rank()` (LINQ + аллокация списка), **binder-IPC
`setUnderlyingNetworks`** и событие `NetworkChanged`. В сутки ≈ 7300 IPC впустую.

**Причина.** 15-секундный троттлинг `onCapabilitiesChanged` обходится условием
`interesting`:
```csharp
interesting = !_networks.TryGetValue(handle, out var old)
              || old.NotMetered != entry.NotMetered
              || old.Validated  != entry.Validated
              || old.Transport  != entry.Transport;
```
Второстепенная сеть (LTE при активном Wi-Fi) регулярно теряет и возвращает `VALIDATED`,
поэтому `interesting` истинно почти всегда и троттлинг не срабатывает.

**Правка по существу:** троттлинг здесь — не тот инструмент. `Publish` должен быть
no-op, когда **итоговый ранжированный список не изменился** (сравнивать
последовательность `NetworkHandle`, а не только голову). Тогда флаппинг `VALIDATED`
на сети, которая всё равно вторая в списке, ничего не стоит, а реальное изменение
порядка проходит немедленно, без 15-секундной задержки.

> Отмечу: `handover` определяется корректно и **не** ложносрабатывает — из 134
> публикаций `handover=True` было ровно 2, оба раза по делу (см. §«подтверждено»).
> Проблема только в холостых публикациях.

## 6. UTF-8 BOM ломает первую строку `events.jsonl` и `crash.log`

```
first 6 bytes: efbbbf7b2274      (ef bb bf = UTF-8 BOM, затем {"t)
first line parses: FAILS -> JSONDecodeError
```

`Encoding.UTF8` в .NET — это `UTF8Encoding(encoderShouldEmitUTF8Identifier: true)`,
и `File.AppendAllText` пишет преамбулу при создании файла. Формат JSON Lines этого не
допускает: строгий построчный парсер спотыкается на первой записи.

Тот же BOM виден в начале `crash.log`.

**Правка:** `new UTF8Encoding(false)` в `EventLog.WriteBatch` и `CrashHandler.Capture`.

## 7. ⚠️ `ControlPacketSize = 96` может принять выгрузку за мёртвый outbound

Живой сэмпл со здорового туннеля (из снимка состояния во время теста):
```
lastSample: out 659809B, back 8807B in 112p
```
Средний входящий пакет = 8807 / 112 ≈ **78 байт**, то есть ниже порога
`ControlPacketSize = 96`. Одновременно `starved` истинно (8807 × 8 < 659809).
Оба условия выполнены → сэмпл считается подозрительным.

Туннель при этом был исправен: `preflight` прошёл, `ifconfig.me` возвращал IP узла.

Спасло то, что нужны **два подряд** таких сэмпла (`SuspicionLimit = 2`), а следующий
замер был здоровым (`out 39117B, back 50029B in 89p`). Но при **длительной** выгрузке —
отправке видео, бэкапе фото — поток чистых TCP ACK даёт именно такую картину много
замеров подряд, и монитор объявит `OutboundDead` с перестройкой туннеля посреди выгрузки.

⚠️ Порог подбирался по замерам с мёртвого outbound (43 байта/пакет), но не проверялся
против честной выгрузки. Нужен замер под нагрузкой, прежде чем менять число: 78 и 43
различимы, но запас невелик. Возможный выход — не полагаться на средний размер пакета,
а прямо спросить ядро (`XrayQueryStats` из отложенных пунктов плана: если xray
отправляет наружу и получает ответы, вопрос снимается без эвристики).

## 8. Предложение: привязка к `libxray.h`

Вы спросили, можно ли переписать привязку на заголовочный файл, который лежит рядом
с библиотекой.

**Напрямую — нельзя, и не нужно.** В C# нет `#include`; `[DllImport]`/`[LibraryImport]`
резолвят символ по имени в рантайме, а типы берут из C#-сигнатуры. Заголовок — артефакт
для C/C++ вызывающих. Именно это и написано в `libxray/README.md`: «C and C++ callers
want it; P/Invoke callers do not need it».

**Но польза у него есть, другая.** `libxray.h` — авторитетное объявление того, что
библиотека действительно экспортирует. Из него можно сделать **проверку контракта на
этапе сборки**: MSBuild-таргет парсит заголовок, собирает список функций и сверяет с
`[DllImport]`-объявлениями в `XrayInterop.cs`.

Что это ловит:
- расхождение приложения и ядра — сейчас оно всплывает только в рантайме как
  `EntryPointNotFoundException`, который я специально глушу (чтобы старое ядро не роняло
  приложение), то есть **тихо**;
- изменение сигнатуры при пересборке ядра — сейчас не ловится вообще и приводит
  к порче стека.

Это тот же класс защиты, что `SocksPortContractTests` и `GuardWindowsNativeCore`:
ошибка ловится на сборке, а не у пользователя. Работы — на полдня.

## Замечания по тестовому окружению

1. **Прод-приложение мешает тестам.** `com.horus.vpn` дважды перехватывал VPN-слот,
   отзывая туннель тестовой сборки через ~11 с после подключения (в журнале это
   `[intent] vpn intent cleared` + `[tun] service destroyed`). Первично я принял это
   за баг. Прод возвращался даже после `am force-stop` — вероятно, через
   Quick-Settings-тайл при открытии шторки. Пришлось `pm disable-user`;
   **после тестов включено обратно** (`pm enable`, проверено — отключённых пакетов нет).

2. **VPN-разрешение сейчас у тестовой сборки.** Android держит согласие только для
   одного приложения. При первом запуске прода система снова спросит разрешение —
   это нормально, но стоит знать.

3. **Тестовый APK остался установлен** (`com.horus.vpn.test`, лейбл «Horus TEST»).
   Удалить: `adb uninstall com.horus.vpn.test`.

4. **`dotnet build` без `EmbedAssembliesIntoApk=true` даёт неработающий APK** —
   Fast Deployment ожидает ассембли, залитые отдельно, и приложение падает на старте с
   `No assemblies found in … .__override__`. Для standalone-APK флаг обязателен.

5. Изменённый на время тестов лейбл в `AndroidManifest.xml` возвращён (`git checkout`).
   Правка воркфлоу в `Xray-core-RTC` — **не** тестовая и остаётся.

## Заметка про режим «Автовыбор»

При адаптации выяснилось, что `MainViewModel.ResolveServerAsync` в автоматическом режиме
подбирал конкретный узел локально и возвращал его. С новым API это означало бы вызов
`POST /servers/select` с этим id на **каждом** подключении, то есть перепривязку аккаунта и
ре-провижининг узла при каждом нажатии «Подключить».

Исправлено: в автоматическом режиме возвращается `null`, привязка не трогается.
«Автовыбор» теперь значит «мне всё равно, какой узел», а не «дай новый». Аккаунт без
привязки по-прежнему получает её автоподбором на стороне `GET /servers/connect`.
Отображаемый сервер берётся из `connection.Server` — это авторитетный ответ API, и он
содержит имя узла, которого в каталоге кандидатов нет.
